Materi course ini:
Pelajari bagaimana Google Cloud Observability membantu tim DevOps melihat kondisi dan performa aplikasi berbasis cloud secara end-to-end. Kamu akan memahami peran Cloud Monitoring, Cloud Logging, Error Reporting, Cloud Trace, dan Cloud Profiler beserta contoh use-case agar siap dipakai saat aplikasi mulai bermasalah.

Materi membahas Google Cloud Observability sebagai paket alat untuk pemantauan dan debugging aplikasi berbasis cloud secara menyeluruh. Inti besarnya: Observability memberi insight tentang kondisi, performa, dan ketersediaan aplikasi sehingga tim bisa menemukan serta memperbaiki masalah lebih cepat. Di dalamnya ada beberapa komponen utama: Cloud Monitoring, Cloud Logging, Error Reporting, Cloud Trace, dan Cloud Profiler. Tutor bisa mengaitkan semuanya dengan alur kerja troubleshooting: mulai dari gejala performa (metrik), lalu cari konteks kejadian (log), konfirmasi kegagalan (error), uraikan latensi antar komponen (trace), dan akhirnya bedah penyebab performa dari sisi konsumsi resource (profiler).

Pertama, Cloud Monitoring & metrik. Materi menekankan bahwa pemantauan dimulai dari data sinyal. Sinyal adalah data mentah/kejadian yang kemudian diproses secara matematis menjadi metrik yang selaras terhadap waktu. Contoh yang diberikan: CPU mentah diukur lalu dihitung rata-ratanya untuk menghasilkan satu nilai per menit. Dengan pendekatan ini, sistem bisa menampilkan tren dan kondisi secara konsisten. Google Cloud secara default mengumpulkan lebih dari seribu aliran data metrik; metrik-metrik ini bisa dimasukkan ke dasbor, pemberitahuan, dan berbagai alat penting lain. Materi juga menyebut Metrics Explorer yang digunakan untuk menavigasi diagram metrik dan melakukan analisis.

Lalu studi kasus BigQuery & Cloud Run untuk memperjelas kenapa metrik penting. Untuk BigQuery, data scientist perlu tahu berapa banyak kueri yang sedang aktif, berapa byte yang telah dipindai dan ditambahkan ke tagihan, serta pola penggunaan slot data. Ini menghubungkan observability dengan biaya dan kapasitas. Untuk Cloud Run (aplikasi dalam container), tim DevOps perlu mengetahui pemakaian CPU dan memori, serta waktu tagihan aplikasi. Materi juga mengangkat ide peningkatan metrik sinyal dari aplikasi kustom di mana pun aplikasi berjalan melalui OpenTelemetry open source agar aplikasi mengekspor metrik sendiri (bukan hanya metrik bawaan).

Selanjutnya, Compute Engine & monitoring. Workload di Compute Engine mendapat manfaat dari data pemakaian CPU dan memori, waktu operasional, throughput disk, dan metrik lain. Cloud Monitoring mengumpulkan metrik, peristiwa, dan metadata dari berbagai sumber: log, layanan, sistem, agen, kode kustom, serta komponen aplikasi umum (contoh yang disebut: Cassandra, NGINX, Apache Web Server, Elasticsearch). Monitoring kemudian menyerap data tersebut dan membuat insight melalui dasbor, diagram Metrics Explorer, serta pemberitahuan otomatis. Tutor sebaiknya menekankan bahwa observability tidak hanya memantau satu sumber, tetapi menggabungkan banyak komponen.

Bagian Cloud Logging membahas dua hal besar: eksplorasi dan ekspor. Logs Explorer diintegrasikan dan menjadi tempat awal untuk analisis log. Entri logging bisa diekspor untuk analisis alternatif/lanjutan. Materi memberi contoh penggunaan hampir real-time pada pesan Pub/Sub dengan kode kustom atau stream processing seperti Dataflow. BigQuery dapat memeriksa data logging melalui kueri SQL. Arsip file log di Cloud Storage juga dapat dianalisis dengan berbagai alat. Data log dapat diekspor sebagai file ke Cloud Storage, pesan melalui Pub/Sub, atau ke dalam tabel BigQuery. Selain itu, metrik berbasis log bisa dibuat dan diintegrasikan ke dashboard, pemberitahuan, dan SLO layanan di Cloud Monitoring.

Tutor juga perlu menjelaskan retensi log. Retensi default bergantung pada jenis log. Materi menyebut log akses data default tersimpan 30 hari dan bisa dikonfigurasi menjadi 3650 hari. Log admin default disimpan 400 hari. Jika butuh memperpanjang retensi, ekspor log ke Cloud Storage atau BigQuery bisa dilakukan. Ini penting untuk strategi kepatuhan (compliance) dan audit investigasi jangka panjang.

Kemudian kategori log. Cloud Logging yang terlihat bervariasi tergantung resource Google Cloud dalam project atau organisasi. Tetapi materi menekankan empat kategori utama: log audit, log agen, log jaringan, dan log layanan. Cloud Audit Logs menjawab pertanyaan “Siapa melakukan apa, di mana, dan kapan?”. Aktivitas admin melacak perubahan konfigurasi. Akses data melacak panggilan yang membaca konfigurasi atau metadata resource dan panggilan berbasis pengguna yang membuat, mengubah, atau membaca data resource. Peristiwa sistem adalah tindakan administratif non-manusia yang mengubah konfigurasi resource. Transparansi Akses mencatat tindakan yang dilakukan personel Google saat mengakses konten Anda. Tutor bisa memandu siswa agar memahami bahwa log audit lebih fokus ke perubahan/akses (siapa-apa-kapan), bukan performa.

Bagian log agen & jaringan. Log agen menggunakan agen Fluentd yang disesuaikan dan dikemas oleh Google dan dapat diinstal di VM AWS atau Google Cloud untuk menyerap data log dari instance (contoh Compute Engine, VM terkelola, container) dan juga instance AWS EC2. Log jaringan menyediakan telemetri operasi jaringan dan keamanan. Log Alur VPC mencatat sampel alur jaringan VPC dan dapat digunakan untuk pemantauan jaringan, forensik, analisis keamanan real-time, serta pengoptimalan biaya. Firewall Rules Logging mendukung audit, verifikasi, dan analisis efek aturan firewall. Log Gateway NAT mencatat informasi koneksi dan error jaringan NAT.

Bagian log layanan & Error Reporting. Log layanan memberikan akses ke log buatan developer yang mengirim kode ke Google Cloud. Contoh: jika developer menggunakan Node.js membangun dan mendeploy container ke Cloud Run, logging ke Standard Out atau Standard Error otomatis dikirim ke Cloud Logging sehingga terpusat dan mudah diakses. Error Reporting menghitung, menganalisis, dan menghimpun error di layanan cloud aktif. Materi menyebut bahwa dalam kebanyakan bahasa modern, error adalah “pengecualian” yang tidak selalu terdeteksi dan ditangani kode secara eksplisit. Antarmuka Error Reporting menampilkan hasil yang bisa diurutkan dan difilter. Tampilan khusus menampilkan detail error: diagram waktu, kemunculan, jumlah pengguna terdampak, pertama/terakhir terlihat, dan stack trace pengecualian yang dibersihkan.

Cloud Trace. Materi menjelaskan kamu bisa membuat pemberitahuan untuk menerima notifikasi error baru. Cloud Trace adalah sistem pelacakan berdasarkan alat Google pada layanan produksinya, yang mengumpulkan data latensi dari aplikasi terdistribusi dan menampilkannya di Konsol Google Cloud. Cloud Trace dapat mencatat trace untuk aplikasi di App Engine, Compute Engine, dan container Kubernetes Engine. Insight performa disediakan hampir real-time; Cloud Trace otomatis menganalisis trace aplikasi untuk membuat laporan latensi mendalam, memunculkan penurunan performa, dan terus-menerus mengumpulkan serta menganalisis data untuk mengidentifikasi perubahan terbaru pada performa.

Cloud Profiler. Materi menggambarkan masalah kode berperforma buruk yang menaikkan latensi dan biaya, namun sering tidak diketahui. Cloud Profiler mengubah situasi itu dengan teknik statistik dan instrumentasi berdampak sangat rendah yang berjalan di semua instance aplikasi produksi. Ia memberi gambaran heap aplikasi dan CPU yang lengkap tanpa memperlambat. Dukungan platform mencakup VM Compute Engine, App Engine, dan GKE. Ia juga mendukung bahasa Java, Go, Python, dan Node.js. Cloud Profiler menampilkan hierarki panggilan dan konsumsi resource fungsi terkait dalam flame graph sehingga developer paham jalur mana yang memakai resource terbanyak, termasuk berbagai cara Cloud Profiler memanggil kode.

Untuk AI tutor, gaya mengajar sebaiknya friendly dan seperti memandu investigasi nyata. Tutor bisa menanyakan: jika metrik menunjukkan lonjakan latensi, mulai dari metrik (Monitoring), lalu cek log (Logging) untuk konteks, verifikasi error (Error Reporting), lihat alur latensi (Trace), lalu gunakan flame graph (Profiler) untuk target optimasi. Ajarkan juga keterkaitan dengan biaya dan kapasitas: monitoring metrik BigQuery/Cloud Run membantu memahami dampak biaya selain performa.
