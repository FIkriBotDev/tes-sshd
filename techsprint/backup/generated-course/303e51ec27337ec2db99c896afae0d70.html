Course: REST API dalam Teknologi Rekayasa Internet

Materi membahas perbandingan antara traditional web applications yang dibangun di atas HTML dan HTTP, dengan pendekatan API, khususnya Web API berbasis HTTP. Traditional web applications cenderung kurang optimal karena client harus memahami HTML/HTTP, halaman biasanya diganti seluruhnya, transisi antar halaman sulit dianimasikan, dan data yang sama dapat dikirim berulang kali dalam beberapa respons. Selanjutnya materi memperkenalkan konsep REST sebagai gaya arsitektur untuk sistem hypermedia terdistribusi. REST dijelaskan melalui batasan arsitektur (client-server, stateless, cache, uniform interface, layered system, code-on-demand) serta makna nama REST (Representational State Transfer). Materi juga menguraikan konsep dasar REST berupa resources (Nouns), penggunaan URI untuk mengidentifikasi resource, dan relasi verb berbasis metode HTTP (CRUD) dengan representasi data (misalnya XML/JSON) yang ditentukan oleh header Accept dan Content-Type. Bagian akhir materi memberi contoh penerapan REST pada layanan (online shopping, search, dictionary, hingga contoh seperti Google Maps atau API pencarian), menjelaskan pola penggunaan metode HTTP (GET, POST, PUT, DELETE, PATCH) beserta kode status HTTP (misalnya 200 OK, 201 Created, 204 No Content, 404 Not Found), serta menyinggung prinsip mendesain REST API agar mudah digunakan programmer lain (misalnya konsistensi endpoint, dan praktik pada contoh Facebook/Twitter).

Chapter 1: Traditional Web Applications vs API (Web API) dan Jenis Web API

Traditional web applications membangun antarmuka di atas HTML dan HTTP. Alur umum dimulai dari browser/client yang mengirim request menggunakan metode GET ke sebuah resource, server merespons dengan status seperti 200 OK serta isi berupa HTML (misalnya <html>Code...</html>). Lalu pengguna mengklik link dan client kembali mengirim request ke halaman/resource lain untuk menampilkan halaman berikutnya.

Dengan pendekatan ini, terdapat beberapa kekurangan. Pertama, client harus memahami HTTP dan HTML. Kedua, seluruh halaman web biasanya diganti dengan halaman lain, sehingga sulit membangun pengalaman pengguna yang mulus. Ketiga, tidak ada cara yang baik untuk menganimasikan transisi antar halaman web. Keempat, data yang sama seringkali dikirim berulang kali dalam beberapa tanggapan, misalnya untuk kode HTML layout yang sebenarnya bisa dipakai ulang.

Materi menekankan bahwa HTTP & HTML dapat digunakan untuk komunikasi, tetapi tidak optimal—contohnya pada GUI smartphone yang tidak menggunakan HTML secara langsung. Karena itu muncul kebutuhan terhadap antarmuka mesin-ke-mesin yang lebih terstruktur. Konsep API didefinisikan sebagai antarmuka untuk komunikasi Mesin ↔ Mesin. Jika API memakai HTTP, maka disebut Web API. Sebagai pembanding, GUI adalah interface untuk komunikasi Manusia ↔ Mesin.

Selain REST, materi juga menyebut berbagai jenis Web API: Remote Procedure Call (RPC), Remote Method Invocation (RMI), dan Representational State Transfer (REST). Pada RPC, client memanggil fungsi di server. Pada RMI, client memanggil metode pada objek di server. Pada REST, client menerapkan operasi CRUD pada resources di server. Aplikasi yang memakai REST banyak ditemui pada layanan seperti online shopping, search services, dan dictionary services.

Chapter 2: Konsep REST: Apa itu REST, Batasan Arsitektur, dan Resource/URI

REST (Representational State Transfer) adalah gaya arsitektur untuk sistem hypermedia terdistribusi yang dijelaskan oleh Roy Thomas Fielding dalam disertasi doktoralnya tahun 2000. REST terdiri dari batasan arsitektur, yaitu: Client-Server, Stateless, Cache, Uniform Interface, Layered System, dan Code-On-Demand. Bersama-sama, batasan-batasan ini membentuk cara kerja sistem web terdistribusi yang konsisten dan mudah diintegrasikan.

Nama REST dimaksudkan untuk menggambarkan bagaimana aplikasi web yang dirancang dengan baik berperilaku: jaringan halaman web (dapat dipandang sebagai virtual state machine). Pengguna melanjutkan aplikasi dengan memilih link yang menyebabkan state transition. Halaman berikutnya (yang merepresentasikan status aplikasi berikutnya) ditransfer ke client dan kemudian dirender untuk digunakan. Dari disertasi Roy, gambaran ini menekankan bahwa perpindahan state berlangsung melalui interaksi berbasis resource dan representasinya.

Materi memperkenalkan konsep REST dengan model nouns dan verbs. Nouns berarti resources (contoh: http://example.com/employees/12345). Verbs dibatasi/terstruktur melalui metode HTTP. Contoh verb yang digunakan adalah GET, sementara representasi data juga dibatasi dan dapat berupa XML atau JSON.

Dalam REST, resource diidentifikasi menggunakan URI (Uniform Resource Identifier), yang bisa setara dengan URL dalam praktik umum. Materi memberi contoh resource seperti halaman web (HTML page) dan menjelaskan pemetaan “client → resource”. Misalnya client memiliki resource http://weather.example.com/oaxaca dan merenderkan OaxacaWeather.html.

Contoh interaksi status pada REST juga dijelaskan melalui operasi pada resource pengguna. Saat client melakukan GET /users/2, server mengembalikan representasi data (misalnya JSON seperti {"id": 2, "name": "Bob"}). Lalu untuk mengubah status, client menggunakan PUT /users/2 dengan representasi baru (misalnya {"id": 2, "name": "Obi"}).

Chapter 3: Menggunakan HTTP untuk CRUD dalam REST API + Desain Endpoint

REST based web services dapat digunakan pada berbagai skenario seperti online shopping, search services, dan dictionary services. Materi mencontohkan REST pada layanan seperti Google Maps dan beberapa API pencarian (misalnya Google AJAX Search API, Yahoo Search API, serta Amazon Web Services). Inti penggunaannya adalah memanfaatkan HTTP sebagai interface yang seragam.

Dalam REST, gunakan URI untuk mengidentifikasi resource. Lalu gunakan metode HTTP untuk menentukan operasi CRUD: Create menggunakan POST (atau PUT), Retrieve menggunakan GET, Update menggunakan PUT (atau PATCH), dan Delete menggunakan DELETE. Selain itu, materi menekankan penggunaan header HTTP Content-Type dan Accept untuk menentukan format data resource. Kemenangan/ kegagalan operasi direpresentasikan melalui kode status HTTP.

Materi memberikan contoh yang menunjukkan perbedaan antara request yang “buruk” dan “baik” dari sisi REST. Contoh “bad” seperti POST /login atau POST /create-book dapat terasa kurang resourceful, sedangkan “good” seperti POST /login-sessions dan POST /books mendekati pola resource. Untuk mengambil data top-10 books, contoh “bad” menggunakan GET /get-top-10-books, sedangkan yang “good” menggunakan resource yang lebih jelas seperti GET /top-10-books.

Lebih rinci, materi menunjukkan contoh endpoint untuk resource pengguna. Untuk mengambil daftar atau detail pengguna, digunakan GET seperti GET /users, GET /users/2, hingga variasi filter dan parameter. Contoh filter bisa menggunakan parameter query, misalnya GET /users?page=1, GET /users?gender=female, GET /users?age=18, atau gabungan GET /users?gender=female&age=18. Untuk data format, client menggunakan header Accept (misalnya Accept: application/json) agar server merespons representasi JSON, sementara jika Accept berupa XML, maka server bisa merespons XML.

Untuk operasi POST, server digunakan untuk membuat resource. Format data yang dikirim ditentukan oleh Content-Type, sedangkan format representasi yang diminta ditentukan oleh Accept. Contoh hasil pembuatan biasanya mengembalikan 201 Created serta header seperti Location (misalnya Location: /users/3), dan sering memuat payload representasi resource baru dalam format sesuai request.

Untuk PUT, materi menjelaskan pembaruan seluruh resource pada URI tertentu (misalnya PUT /users/3), dengan status 204 No Content jika tidak mengirim body respons. Materi juga menekankan bahwa PUT dapat dipakai untuk membuat sumber daya jika URI yang harus dimiliki sumber daya berikutnya sudah diketahui. Untuk DELETE, gunakan DELETE /users/2 dan server dapat merespons 204 No Content. Untuk pembaruan parsial, digunakan PATCH seperti PATCH /users/1, dengan catatan PATCH adalah standar yang diusulkan (dalam konteks materi).

Bagaimana jika terjadi kesalahan? Materi menegaskan bahwa cara yang tepat adalah menggunakan kode status HTTP. Contoh: GET /users/999 dengan Accept JSON dapat menghasilkan 404 Not Found. Pesan kesalahan dapat disertakan di response body secara opsional, dan materi mengarahkan pembaca untuk merujuk daftar kode status HTTP.

Akhirnya materi membahas prinsip mendesain REST API. Tujuannya agar API semudah mungkin digunakan oleh programmer lain. Contoh praktik yang disebutkan: selalu berusaha konsisten pada status sukses (misalnya selalu return 200 OK) dan menggunakan pola endpoint yang jelas. Materi memberi contoh gaya endpoint ala Facebook (misalnya GET /v2.7/{user-id}, GET /v2.7/{post-id}, GET /v2.7/{user-id}/friends, GET /v2.7/{object-id}/likes) dan contoh gaya ala Twitter (misalnya hanya menggunakan GET dan POST, serta endpoint seperti GET /1.1/users/show.json?user_id=... dan POST /1.1/favorites/destroy.json?id=...).
