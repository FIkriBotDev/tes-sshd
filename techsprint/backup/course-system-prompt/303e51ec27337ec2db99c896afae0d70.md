Materi utama:
Materi membahas perbandingan antara traditional web applications yang dibangun di atas HTML dan HTTP, dengan pendekatan API, khususnya Web API berbasis HTTP. Traditional web applications cenderung kurang optimal karena client harus memahami HTML/HTTP, halaman biasanya diganti seluruhnya, transisi antar halaman sulit dianimasikan, dan data yang sama dapat dikirim berulang kali dalam beberapa respons.

Selanjutnya materi memperkenalkan konsep REST sebagai gaya arsitektur untuk sistem hypermedia terdistribusi. REST dijelaskan melalui batasan arsitektur (client-server, stateless, cache, uniform interface, layered system, code-on-demand) serta makna nama REST (Representational State Transfer). Materi juga menguraikan konsep dasar REST berupa resources (Nouns), penggunaan URI untuk mengidentifikasi resource, dan relasi verb berbasis metode HTTP (CRUD) dengan representasi data (misalnya XML/JSON) yang ditentukan oleh header Accept dan Content-Type.

Bagian akhir materi memberi contoh penerapan REST pada layanan (online shopping, search, dictionary, hingga contoh seperti Google Maps atau API pencarian), menjelaskan pola penggunaan metode HTTP (GET, POST, PUT, DELETE, PATCH) beserta kode status HTTP (misalnya 200 OK, 201 Created, 204 No Content, 404 Not Found), serta menyinggung prinsip mendesain REST API agar mudah digunakan programmer lain (misalnya konsistensi endpoint, dan praktik pada contoh Facebook/Twitter).

Materi ini membahas REST API dalam konteks “Teknologi Rekayasa Internet”. Awalnya materi menempatkan traditional web applications sebagai pendekatan lama: antarmuka dibangun di atas HTML dan HTTP. Pola interaksi yang dijelaskan mirip alur browser tradisional: client mengirim request (umumnya menggunakan GET) ke sebuah endpoint resource, server merespons dengan status seperti 200 OK dan mengembalikan dokumen HTML. Pengguna kemudian mengklik link sehingga terjadi request berikutnya untuk halaman resource lain. Hal ini membentuk “navigasi berbasis halaman”, di mana setiap perpindahan link memicu penggantian halaman.

Materi kemudian menyoroti sejumlah kekurangan pendekatan tersebut. Client harus memahami detail HTTP dan HTML; pada banyak kasus seluruh halaman harus diganti setiap kali navigasi terjadi, sehingga transisi antar halaman tidak mudah dianimasikan; data yang sama (misalnya komponen layout) dapat dikirim berulang dalam beberapa respons. Materi juga menekankan ketidakefisienan untuk perangkat dengan GUI yang tidak berbasis HTML (contohnya smartphone), sehingga walaupun HTTP & HTML bisa dipakai, implementasinya tidak optimal untuk kebutuhan integrasi “mesin ke mesin”. Dari sini materi mengarah pada penggunaan API sebagai antarmuka komunikasi antar sistem.

API didefinisikan sebagai antarmuka untuk komunikasi Mesin ↔ Mesin. Jika API menggunakan HTTP, maka disebut Web API. Materi membandingkan juga peran GUI (Manusia ↔ Mesin) dengan API (Mesin ↔ Mesin), dengan ilustrasi konsep: server menyediakan API, client memanggil API, dan user berinteraksi lewat GUI. Setelah itu materi mengenalkan berbagai jenis Web API: RPC (Remote Procedure Call) di mana client memanggil fungsi pada server; RMI (Remote Method Invocation) di mana client memanggil metode pada objek di server; serta REST (Representational State Transfer) di mana client menerapkan operasi CRUD pada resources di server.

Bagian penting berikutnya menjelaskan definisi REST. REST adalah gaya arsitektur untuk sistem hypermedia terdistribusi; sumber rujukannya adalah Roy Thomas Fielding (disertasi 2000). Materi menyebut batasan arsitektur REST: Client-Server (pemisahan peran client dan server), Stateless (setiap request independen, tidak menyimpan state di server), Cache (respons seharusnya dapat di-cache), Uniform Interface (antarmuka operasi seragam), Layered System (sistem dapat tersusun berlapis), dan Code-On-Demand (opsional: server dapat mengirim kode yang dijalankan client). Materi menjelaskan juga makna nama REST: Representational State Transfer—menggambarkan perilaku aplikasi web terdistribusi seperti state machine virtual. Pengguna memilih link sebagai state transition; halaman berikutnya mewakili status aplikasi baru dan ditransfer serta dirender untuk digunakan. Ini memberi landasan bahwa state perubahan terkait dengan representasi resource dan transisi yang dihasilkan melalui interaksi client.

Materi lalu memperkenalkan konsep noun-verb dalam REST. Nouns merepresentasikan resources (contoh struktur URI seperti /employees/12345). Verbs (operasi) dibatasi dan diwujudkan melalui metode HTTP, sedangkan representasi dibatasi pada format seperti XML/JSON. Di sini materi menekankan resource diidentifikasi oleh URI (Uniform Resource Identifier, sering dipraktikkan sebagai URL). Contoh weather resource dan mapping ke halaman yang dirender diberikan untuk menggambarkan relasi resource ↔ representasi. Materi juga menggambarkan contoh interaksi user: GET /users/2 mengembalikan JSON representasi user, lalu PUT /users/2 mengubah representasi/state user dengan data baru.

Setelah fondasi konsep, materi beralih pada praktik: bagaimana menggunakan HTTP sebagai interface seragam untuk REST API. Prinsipnya: gunakan URI untuk resource; gunakan metode HTTP untuk CRUD (Create: POST atau PUT; Retrieve: GET; Update: PUT atau PATCH; Delete: DELETE). Untuk format data, materi menekankan peran header Content-Type dan Accept. Accept mengatur format representasi yang client inginkan dari server. Content-Type menyatakan format data yang dikirim client ke server. Server menggunakan kode status HTTP untuk menunjukkan keberhasilan/kegagalan. Materi menekankan pula bahwa REST adalah gaya arsitektur, bukan spesifikasi ketat; dalam praktik, bisa ada variasi implementasi, tetapi beberapa praktik lebih baik daripada yang lain. Materi mengarahkan referensi “Web API Design - Crafting Interfaces that Developers Love” sebagai panduan desain API yang baik.

Bagian praktik REST menggunakan contoh “server dengan informasi pengguna”. Untuk operasi retrieval, materi mencontohkan endpoint seperti GET /users, GET /users/2, serta bentuk pencarian/filter melalui query parameters (page, gender, age). Materi menunjukkan bahwa format data respons tergantung Accept; contoh jika Accept: application/json maka server merespons JSON berisi array objek user. Dengan pola serupa, materi menjelaskan operasi POST untuk membuat resource baru: POST /users, dengan contoh pengiriman XML (Content-Type: application/xml) dan permintaan respons JSON (Accept: application/json). Respons pembuatan lazimnya 201 Created dan dapat menyertakan Location header ke URI resource baru (misalnya /users/3). Untuk PUT, materi menunjukkan pembaruan seluruh resource pada URI spesifik (misalnya PUT /users/3) dan server bisa mengembalikan 204 No Content jika tidak perlu body. Materi juga menambahkan bahwa PUT bisa dipakai untuk membuat sumber daya bila URI target sudah diketahui.

Untuk penghapusan, materi mencontohkan DELETE /users/2 dengan respons 204 No Content. Untuk pembaruan parsial, materi menunjukkan PATCH /users/1 dengan contoh payload parsial dan respons 204 No Content; materi mencatat PATCH adalah standar yang diusulkan (sesuai wording materi). Penanganan error juga dijelaskan: gunakan kode status HTTP seperti 404 Not Found ketika resource tidak ada (misalnya GET /users/999). Materi juga menyarankan membaca daftar kode status HTTP untuk rujukan lebih lengkap dan menyebut bahwa pesan kesalahan dalam body adalah opsional.

Terakhir, materi mengulas mendesain REST API. Prinsip utama: buat API semudah mungkin untuk digunakan programmer lain. Materi memberikan contoh praktik seperti konsistensi pada status sukses (contoh “selalu return 200 OK” sebagai rekomendasi dalam materi) dan penggunaan endpoint yang rapi serta mengikuti pola resource. Contoh gaya Facebook menunjukkan versioning pada path (/v2.7/) dan struktur resource-relasi (user/friends, object/likes). Contoh gaya Twitter menekankan pembatasan metode (hanya GET dan POST) serta struktur endpoint yang membawa parameter (misalnya show.json?user_id=..., dan favorites/destroy.json?id=...). Keseluruhan materi menekankan bahwa REST dapat diterapkan secara praktis dengan memadukan konsep resources, URI, metode HTTP, representasi data (XML/JSON via Accept/Content-Type), serta kode status HTTP untuk membangun layanan yang jelas dan terstruktur.
